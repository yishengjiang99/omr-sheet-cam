### Expected
If `loadTransferable` fails for an iCloud-only asset, the PHAsset+network fallback actually works (or is removed and the error message is clear).

### Actual
`PhotoLibraryImport.loadData` falls back to `PHAsset.fetchAssets(withLocalIdentifiers:)` and `PHImageManager.requestImageDataAndOrientation`, which require Photos authorization. `rg requestAuthorization|PHPhotoLibrary Sources` finds no authorization request anywhere (PhotosPicker itself is out-of-process and needs none), so with `.notDetermined` the fetch returns no asset and the user gets the generic "Could not load that photo". The fallback is therefore likely dead code on first use. (`NSPhotoLibraryUsageDescription` is set but unused.) Mitigation: `loadTransferable(type: Data.self)` usually handles iCloud download itself, so impact is limited to rare cases.

### Location
- `Sources/App/Capture/PhotoLibraryImport.swift:36-62` (fallback)
- `Sources/App/Capture/PhotoLibraryImport.swift:43-46` (fetch returns nil -> noData)
- `Sources/App/Player/LibraryScreen.swift:192-205 and Sources/App/Capture/CameraScreen.swift:244-257` (error surfaces)
Root cause (1-2 lines): Fallback depends on a permission the app never requests.

### Repro
1. Device with Optimize iPhone Storage, a photo not downloaded, Wi-Fi on, fresh install (Photos permission undetermined).
2. Pick that photo; if `loadTransferable` throws, observe "Could not load that photo".

Repro rate: needs device only (not reproduced)
Evidence: static trace at HEAD with file:line above (no screenshot/recording yet)

### Severity
P3 — rare path; error is handled gracefully.

### Suggested fix
Either request `.readWrite`/limited authorization before using the PHAsset fallback (and handle denial copy), or drop the fallback and show "Download the photo in Photos first" when `loadTransferable` fails.

**Step ID:** F6.8 (also F6.4, P1.4)
**Flow:** F6 Recognition: reading screen, progress, warm-up, cancel
**Static verdict from audit:** GAP (confirmed by code trace; timing is runtime)
**Build / env:** traced at HEAD `736d0f6` (main) · iOS 17+ · static code trace, not yet reproduced on device/Simulator · StoreKit env: Xcode config (needs attach, see P11.3) / Sandbox · Apple ID type: sandbox tester

### Expected
Cancel stops (or at least discards) the in-flight recognition: no Library entry appears later, no orphan JPEG, the next scan starts immediately, quota is not consumed (see P1.4).

### Actual
Cancel calls `dismiss()` only. SwiftUI cancels the `.task`, but `ResultScreen.process()/recognize()` never check `Task.isCancelled`; `PageRecognitionService.Engine.run` awaits non-cancellable detached tasks, and `Engine.recognize` only checks cancellation while still queued. The parse runs to completion (seconds to ~30 s), holding the FIFO `busy` lock, so the next scan waits behind it. When it returns, `recognize` still sets `outcome`, tracks `scan_success`, and calls `saveToPlaylist(d)` - an unexpected "NEW" Library entry appears after the user cancelled. The capture JPEG saved before recognition is left orphaned. The `ReadingView` doc comment claims Cancel "cancels the recognition task".

### Location
- `Sources/App/Capture/ResultScreen.swift:58` (Cancel -> dismiss)
- `Sources/App/Capture/ResultScreen.swift:206-216,245-271` (no cancellation checks; saveToPlaylist at :269)
- `Sources/App/Inference/PageRecognitionService.swift:201-219` (queue; cancel checked only at :214)
- `Sources/App/Inference/PageRecognitionService.swift:231-284` (detached, non-cancellable parse)
- `Sources/App/Capture/ReadingView.swift:5` (comment says it cancels)
- `Tests/PageRecognitionServiceTests.swift:185-203` (covers only cancel-while-queued)
Root cause (1-2 lines): Cooperative cancellation is not plumbed through ResultScreen -> service -> detached parse.

### Repro
1. Scan sample picture; immediately tap Cancel on Reading.
2. Immediately start another scan: Reading shows no progress until the first parse finishes.
3. Return to Library after ~10-30 s: a new scan from the cancelled run appears (NEW).

Repro rate: always (queue/late-save follow from code); durations need device
Evidence: static trace at HEAD with file:line above (no screenshot/recording yet)

### Severity
P2 — confusing wrong behavior with workaround; also contributes to quota/privacy issues.

### Suggested fix
In `recognize`: after `await service.recognize`, `guard !Task.isCancelled else { delete captured JPEG; return }` before setting outcome/saving. In the engine add cancellation checkpoints between stages (ORT cannot abort mid-run; at least skip decode/parse when cancelled before start and use a `cancelled` flag in the progress handler). Delete the orphan JPEG on cancel.

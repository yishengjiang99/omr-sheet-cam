### Expected
One `StoreKitManager` app-wide (one `Transaction.updates` listener, one entitlement refresh), injected into both the gate and the paywall.

### Actual
`ScanQuota` creates a private `StoreKitManager()` (`ScanQuota.swift:11`) and `RootFlowView` creates another `@StateObject StoreKitManager()` (`RootFlowView.swift:15`). Each starts its own `Transaction.updates` task and `refreshEntitlements()`; they communicate only via `UserDefaults["omr.isPro"]`. Both call `finish()` and write the flag (races: one manager's refresh can overwrite the other's fresh grant). Also `Task { [weak self] in await self?.listenForTransactions() }` takes a strong ref for the loop, so `deinit` never cancels it. Behaviour works today only because both read the same defaults key.

### Location
- `Sources/App/Services/ScanQuota.swift:11`
- `Sources/App/RootFlowView.swift:15`
- `Sources/App/Services/StoreKitManager.swift:23-32` (listener task, weak self ineffective)
Root cause (1-2 lines): Singleton quota object owns its dependency instead of receiving the shared manager.

### Repro
1. Add a counter/log in `StoreKitManager.init`; launch app.
2. Observed: 2 inits at launch (ScanQuota.shared + RootFlowView).

Repro rate: always
Evidence: static trace at HEAD with file:line above (no screenshot/recording yet)

### Severity
P3 — no user-visible failure today; complicates fixes for P7.4/P7.6 and doubles StoreKit work.

### Suggested fix
Make one `StoreKitManager.shared` (or inject into `ScanQuota.init(storeKit:)`) and have `RootFlowView` use it via `@ObservedObject`/environment; keep a strong self capture for the listener or use `Task.detached` with explicit cancel.

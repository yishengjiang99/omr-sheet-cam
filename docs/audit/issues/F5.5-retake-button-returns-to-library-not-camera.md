**Step ID:** F5.5 (also F9.5, F7.8)
**Flow:** F5 Scan hand-off gate (handlePhoto)
**Static verdict from audit:** GAP (confirmed by code trace)
**Build / env:** traced at HEAD `736d0f6` (main) · iOS 17+ · static code trace, not yet reproduced on device/Simulator · StoreKit env: Xcode config (needs attach, see P11.3) / Sandbox · Apple ID type: sandbox tester

### Expected
"Retake" / "Retake photo" lands on the Camera ready to shoot again.

### Actual
`handlePhoto` removes the `.camera` route before pushing `.result`, so the stack is `[result]` over Library. The toolbar "Retake" (`result.retake`) and the failure-state "Retake photo" (`result.retakeFromError`) both call `dismiss()`, which pops to Library; the user must tap Camera again. After a failed photo scan (the main reason to retake) this adds a step each time.

### Location
- `Sources/App/RootFlowView.swift:57-63` (camera popped at :60)
- `Sources/App/Capture/ResultScreen.swift:66-71` (Retake = dismiss)
- `Sources/App/Capture/ResultScreen.swift:139-142` (Retake photo = dismiss)
Root cause (1-2 lines): Navigation stack drops the camera route; Retake has no knowledge of the photo source.

### Repro
1. Camera -> shoot -> Reading -> failure (or success) -> tap Retake.
2. Observed: Library. Expected: Camera preview.

Repro rate: always
Evidence: static trace at HEAD with file:line above (no screenshot/recording yet)

### Severity
P2 — UX friction with obvious workaround.

### Suggested fix
Pass `onRetake` closure from `RootFlowView`: for `photo.source == .camera` do `path.removeLast(); path.append(.camera)`; for library/sample sources keep returning to Library (or reopen picker) and rename the label accordingly.

### Acceptance test
- [ ] Manual: After a camera scan, Retake opens the live preview.
- [ ] Automated: Unit test on route reducer: `retake(source:.camera)` produces `[.camera]`; `.library` produces `[]`.
